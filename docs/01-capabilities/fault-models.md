# 故障模型（Fault Models）

[English](fault-models_EN.md) | 简体中文

本文件定义四种特殊故障与弱网整形的行为。所有条目均已实现，其源码位置见文末。边界与已知限制集中于
[限制](limitations.md)，本文不再重复。

理解故障行为需区分两个层次：

- **协议行为**：Pakomo 能够控制的动作，包括拒绝连接、发送 TCP RST、丢弃数据、合成 DNS 响应以及暂存下行数据。
- **应用错误码**：由 Android 网络栈、转发引擎、应用使用的解析器以及 Chromium 版本共同决定。Pakomo 只能设定目标，
  不保证所有设备返回相同的编号。验证时应先确认协议行为是否正确，再记录应用错误码；Chromium `net::Error` 仅作参考。

四种特殊故障相互独立，可同时启用，并随规则保存。运行时按协议类型分别决策，而非以单一分支覆盖全部流量。

## A. 弱网整形

弱网整形提供固定延迟、抖动、丢包与限速，叠加于同一数据面，与特殊故障互不重复施加。

- 简单模式下，延迟、抖动与丢包为整体（往返）值，由整形器均分到上行与下行。
- 高级模式下，每个方向的延迟、抖动与丢包独立设置；带宽本就按方向设置。
- 统计口径（上下行是否独立、丢包发生在哪一层、与测速工具的差异）参见 [测量口径](../06-testing/measurement-methodology.md)。

## B. 连接重置（Connection Reset）

对命中的 TCP 连接，Pakomo 先向隧道侧确认连接建立，再对客户端 Socket 设置 `SO_LINGER(0)` 并立即关闭，
从而促使隧道向应用表现为 TCP RST。目标错误为 `ERR_CONNECTION_RESET (-101)`。

UDP 没有 TCP RST。对 QUIC（UDP 443），Pakomo 只能丢弃数据以尝试促使应用回落到 TCP，是否回落由应用决定，不作保证。

## C. DNS 解析失败（DNS Failure）

DNS 解析失败只改变明文 UDP 53 的查询结果，不影响数据连接。

| 结果 | RCODE | 协议行为 | Chromium 目标（仅参考） |
|---|---:|---|---|
| NXDOMAIN | 3 | 合成 RCODE=3 | `-105 ERR_NAME_NOT_RESOLVED` |
| SERVFAIL | 2 | 合成 RCODE=2 | 常见 `-137`，部分解析器归并为 `-105` |
| REFUSED | 5 | 合成 RCODE=5 | 常见 `-137` |
| 超时 | 无响应 | 丢弃查询 | 由解析器决定 |

合成响应保留事务 ID 与原始 Question，标记为 Response，设置正确的 RCODE，不携带伪造的成功 Answer，
并从原 DNS 服务器地址返回。

"阻止缓存后的连接"是 DNS 故障中的独立开关，默认关闭。已有 DNS 缓存时应用可能不再发起查询，DNS 失败无法改变缓存结果；
开启该开关后，对 DNS 故障目标的 TCP 连接执行重置、对非 DNS UDP 执行丢弃。相应日志使用 `dns-cache-guard-reset` 与
`dns-cache-guard-drop`，不表述为 DNS 响应失败。

## D. 网络中断（Network Blackout）

网络中断只处理目标的数据连接，包括 TCP、非 DNS UDP 与 QUIC，不拦截 DNS 查询（DNS 查询由 DNS 解析失败单独处理）。
如此，未缓存的域名仍可先完成解析，"立即"与"静默"的差异才体现在连接阶段。

- **立即模式**尽快返回主动失败结果，不等待应用超时。当连接建立前即可判定命中时（全局、整应用，或域名对应的目标 IP
  已从明文 DNS 学习到），返回 SOCKS `CONNECTION_REFUSED (0x05)`，目标表现为 `-102`。当域名首次连接、目标 IP 尚未学习时，
  必须先建立连接并读取 TLS SNI 或 HTTP Host，此时 SOCKS SUCCESS 已返回、无法再拒绝，故降级为 RST（`-101`）。
- **静默模式**在确认连接建立后挂起，读取并丢弃客户端数据，不返回任何内容，直至应用超时或达到 Pakomo 的空闲上限，
  目标表现为 `-7 ERR_TIMED_OUT`。非 DNS UDP 与 QUIC 直接丢弃。

网络中断模拟的是目标流量故障，不会使 Android 系统广播真实的网络断开。

## E. 慢响应 / Late Response

慢响应是一个独立的故障模型，与普通网络延迟不同。

| | 普通延迟（整形 A） | 慢响应 / Late Response（E） |
|---|---|---|
| 模拟对象 | 网络传输时间：请求包延迟发送、响应包延迟接收 | 请求已到达服务器侧，服务器长时间不返回业务响应，连接可能仍保持，最终才返回结果 |
| 作用方向 | 上行与下行均可能 | 客户端侧无法真正控制服务器，通过暂存下行数据近似模拟"响应迟到" |
| 叠加关系 | 与特殊故障叠加于同一数据面 | 独立计时，不默认与基础延迟叠加 |

协议行为采用闸门模型。对命中连接的下行方向，第一片被暂扣的下行数据打开闸门，闸门开启时刻为"首个被暂扣分片到达时刻
加上 `holdMs`"。闸门开启前的下行数据全部缓存，到点一次性放行；客户端因此在约 `holdMs` 后开始收到响应，随后全速收完。
闸门开启后到达的数据按自身时间放行。该模型得到恒定的迟到时长，而非将服务器的流式过程整体平移。

- 计时起点为首个被暂扣的下行分片到达时刻。
- 仅作用于 TCP 下行；QUIC 与 UDP 下行不暂扣，属尽力而为，与前三种故障一致。
- 闸门开启前，整份响应缓存在内存中，不设字节上限；超大下载会带来相应的内存开销，属已知取舍。

"放行小响应"阈值（`holdBypassBytes`，默认为 0，表示全部暂扣）指：下行累计不超过该字节数的连接立即放行、不暂扣，
用于放过心跳与探测。该机制为近似，而非可靠的心跳识别：真实心跳可能被加密、分片或封装，按固定字节阈值无法可靠区分
心跳与业务响应的开头。阈值应略大于心跳响应；在同一 keep-alive 连接上，累计字节跨整条连接统计，如果在业务请求前
累计大量心跳并超过阈值，则可能误伤业务响应。

由于不解密 TLS，慢响应作用于连接级别，无法只延迟同一条 HTTP/2 连接内的单个请求而放过心跳。按请求粒度延迟需要
中间人解密，属明确不做的范围，参见 [原则与边界](../00-overview/principles-and-boundaries.md)。

## 按协议执行的优先级

同一目标可被多种故障选中，运行时按协议分别决策：

- **DNS 查询**：先判定 DNS 解析失败，未命中则正常转发；网络中断不处理 DNS 查询。
- **TCP**：依次判定网络中断、DNS 缓存保护（启用时）、连接重置、普通弱网规则，最后对下行施加慢响应。
- **非 DNS UDP**：依次判定网络中断、DNS 缓存保护（启用时）、连接重置的 QUIC 回落辅助、普通弱网规则。

## 目标行为矩阵

下表的 Chromium 编号是验证目标，不构成跨设备保证。

| 故障 | 模式 | 协议行为 | Chromium 目标 |
|---|---|---|---|
| 连接重置 | — | 建立后发送 RST | `-101` |
| 网络中断 | 立即 | 连接前拒绝；无法预判时降级为 RST | `-102`；降级为 `-101` |
| 网络中断 | 静默 | 接受后挂起、不返回数据 | `-7` |
| DNS 失败 | NXDOMAIN | RCODE 3 | `-105` |
| DNS 失败 | SERVFAIL、REFUSED | RCODE 2、5 | 常见 `-137` |
| DNS 失败 | 超时 | 丢弃查询 | 由解析器决定 |
| 慢响应 | — | 下行暂扣 `holdMs` 后放行 | 表现为迟到而非错误，应用侧常见超时、重试与原请求迟到响应 |

## 日志动作名

故障命中使用以下稳定动作名：`pre-connect-refused`、`post-connect-reset`、`silent-park`、`udp-drop`、
`quic-fallback-drop`、`dns-nxdomain`、`dns-servfail`、`dns-refused`、`dns-timeout`、`dns-cache-guard-reset`、
`dns-cache-guard-drop`。日志不记录 DNS 报文正文、HTTP 内容、Cookie、凭据或其他应用数据；同一连接的重复包去重，
重连风暴按秒汇总限速。
