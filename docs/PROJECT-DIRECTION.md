# Pakomo 项目方向

## 1. 项目定位

Pakomo 是一款面向 Android 10+ 的非 Root、按目标生效的网络故障模拟工具。

项目重点不是修改设备的真实网络开关，而是在本地 VPN 转发链路中，对用户明确选择的流量稳定地模拟弱网和连接故障。产品应保持以下特点：

- 不需要 Root。
- 不解密 HTTPS，不安装中间人证书。
- 未命中的流量正常旁路。
- 所有配置保存在本地，不收集流量内容。
- 首页保持简单，复杂配置进入规则和目标选择页面。
- 运行状态、原始日志和实际命中目标可验证。

## 2. 核心配置模型

Pakomo 的运行配置分成三个相互独立的维度。

### 2.1 接管范围

接管范围决定“哪些流量进入模拟逻辑”，三种模式互斥：

- 全局：设备中的目标 IPv4 流量。
- 指定应用：选中的应用；每个应用可以继续限定域名。
- 指定域名：访问指定域名及其子域名的流量。

切换接管范围不改变规则内容。当前范围没有目标时，服务保持空闲运行，不自动停止。

### 2.2 普通弱网规则

普通弱网参数作用于当前接管范围内的全部目标：

- 固定延迟
- 抖动
- 丢包
- 上传、下载限速
- 简单模式与上下行独立的高级模式

### 2.3 特殊故障

特殊故障不是互斥选项，而是三套可以同时启用的独立能力：

1. Connection Reset
2. DNS 解析失败
3. 网络中断

每种故障分别保存：

- 是否启用
- 故障参数
- 生效目标

普通弱网仍作用于整个接管范围，特殊故障只作用于该故障额外选中的目标。

## 3. 特殊故障的目标模型

同一个域名出现在不同范围中时，含义并不相同，因此不能只用域名字符串标识目标。

目标至少需要区分：

- `Global`：当前范围内全部目标。
- `AddressDomain(domain)`：指定域名模式中的域名，对所有应用生效。
- `Application(packageName)`：整个应用。
- `ApplicationDomain(packageName, domain)`：某个应用访问某个域名。

例如：

- `ApplicationDomain(微信, api.example.com)` 只影响微信。
- `AddressDomain(api.example.com)` 在指定域名模式下影响所有应用。

两者可以同时配置，但不能自动联动。

### 3.1 重复与覆盖提示

目标选择页面需要检测并提示以下情况：

- 应用域名同时存在于指定域名列表。
- 同一个域名被多个应用使用。
- 父域名覆盖子域名，例如 `example.com` 覆盖 `api.example.com`。

提示仅用于说明关联关系，不阻止保存，也不自动修改其他模式的选择。

## 4. 界面方向

首页继续只保留：

- 启停与空闲运行状态
- 实时流量
- 当前接管范围
- 规则、日志、域名延迟测试和设置入口

特殊故障放在规则编辑页底部，使用三条独立入口：

- `连接重置　已选 N 个　[开关]`
- `DNS 失败　 已选 N 个　[开关]`
- `网络中断　 已选 N 个　[开关]`

开启某项后，点击该行进入独立的目标选择页面。不要把完整应用和域名列表直接展开在规则编辑页中，以免页面过长并影响滑动性能。

目标选择页面随当前接管范围变化：

- 全局：直接作用于全局，不显示目标列表。
- 指定应用：显示已选应用；有域名配置时可逐个选择域名，没有域名配置时可选择整个应用。
- 指定域名：显示当前指定域名列表。

目标数量为零时保留开关状态，但该故障不触发，并在入口右侧显示 `0`。

## 5. 三类故障的行为

### 5.1 Connection Reset

仅作用于 TCP。支持在连接建立时或连接运行过程中强制重置。

第一阶段至少实现立即重置；后续可扩展：

- 触发概率
- 建立连接后延迟触发
- 传输一定字节数后触发

实现需要验证 SOCKS 转发层关闭连接时，是否能在不同 Android 版本上稳定向应用表现为 TCP RST。必要时调整 HEV 原生转发层。

### 5.2 DNS 解析失败

对普通 UDP/TCP 53 DNS 查询提供三种结果：

- `NXDOMAIN`：域名不存在
- `SERVFAIL`：DNS 服务失败
- 超时：丢弃请求，不返回响应

DNS 查询必须解析问题域名，再结合应用归属和故障目标判断是否命中。

已知限制：

- DoH 和 DoT 内容已加密，无法按查询域名修改。
- QUIC/HTTP3 中的加密解析同样无法直接处理。
- 可以阻断已知加密 DNS 服务，但不能伪造其中的具体解析结果。

### 5.3 网络中断

网络中断只模拟目标流量不可用，不关闭设备的 Wi‑Fi 或移动数据，也不伪造 Android 系统的 `Network lost` 状态。

建议提供两种表现：

- 静默中断：丢弃 TCP/UDP 流量，让应用等待超时。
- 立即失败：拒绝新连接并关闭已有连接。

## 6. 故障重叠规则

三种故障允许同时开启，也允许选择同一个目标。运行时使用固定优先级，避免结果依赖执行顺序：

1. 网络中断优先处理 TCP 和 UDP。
2. 未被网络中断的 DNS 请求再执行 DNS 失败。
3. 未被网络中断的 TCP 连接再执行 Connection Reset。
4. 未命中特殊故障的流量继续使用普通弱网规则。

每次命中都应写入原始日志，并在诊断信息中包含：

- 故障类型
- 接管范围
- 应用名称与包名（可以归属时）
- 域名或目标地址
- 实际执行结果

日志不得记录请求正文、Cookie、凭据或其他应用数据。

## 7. 实施顺序

### 阶段一：配置与界面

- 为三种故障建立独立数据模型和持久化格式。
- 添加规则编辑页的三个开关与数量入口。
- 实现全局、指定应用、指定域名三种目标选择页面。
- 实现精确域名、跨应用重复、父子域名覆盖提示。
- 旧规则升级后默认关闭全部特殊故障。

### 阶段二：网络中断

- 复用现有全阻断能力。
- 区分静默超时和立即失败。
- 支持运行中热更新，不重启 VPN。

### 阶段三：DNS 解析失败

- 解析普通 DNS 查询。
- 实现 NXDOMAIN、SERVFAIL 和超时。
- 按应用、应用域名和指定域名匹配。
- 增加 DNS 压缩、异常报文和 TCP DNS 测试。

### 阶段四：Connection Reset

- 实现新连接立即重置。
- 验证已有连接重置。
- 必要时扩展 HEV 原生前导或控制协议。
- 增加长连接、HTTP/2 和高并发验证。

### 阶段五：可靠性与诊断

- 为三类故障增加独立命中计数。
- 完善原始日志和错误状态。
- 验证规则热切换、范围切换、目标删除和空目标行为。
- 真机覆盖 Android 10 至当前支持版本。

## 8. 验收原则

每项特殊故障完成时至少满足：

- 只影响当前接管范围。
- 只影响该故障明确选中的目标。
- 相同域名在不同模式下不会意外联动。
- 切换规则、范围和目标时可以热更新。
- 清空目标不会停止 VPN。
- 未命中流量与未开启故障时的行为保持不变。
- 日志能够证明实际命中了哪个目标、执行了什么故障。
- 不引入 HTTPS 中间人、不扩大数据收集范围。

## 9. 暂不考虑

- HTTPS 路径级匹配
- 安装本地 CA 或解密应用流量
- 绕过应用证书锁定
- 非 Root 状态下真实关闭系统网络
- 对 DoH/DoT 查询内容进行伪造
